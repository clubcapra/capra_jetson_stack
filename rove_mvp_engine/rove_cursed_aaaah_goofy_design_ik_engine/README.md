# IK Engine — exported from ForgeBOT

A self-contained UDP server that runs the ForgeBOT IK solver over the
Protobuf protocol described in `engine/messages.proto`. The bundle ships
with everything it needs — your robot's URDF, the kinematic chain, and
the IK profile tuned in the editor. Just install numpy and run.

## Layout

```
.
├── README.md
├── requirements.txt
├── run.py                  ← entry point
├── engine/
│   ├── __init__.py
│   ├── server.py           ← UDP server (3 sockets)
│   ├── ik.py               ← FK / Jacobian / resolved-rate / position IK
│   ├── proto.py            ← pure-python protobuf codec (no codegen needed)
│   └── messages.proto      ← canonical schema, for codegen on your side
└── data/
    ├── chain.json          ← serialized kinematic chain
    ├── ik_profile.json     ← tuned IK parameters from `Train IK…`
    ├── robot.urdf          ← exported URDF
    ├── meshes/             ← visual / collision meshes referenced by the URDF
    └── textures/           ← textures referenced by the URDF (if any)
```

## Running

```
pip install -r requirements.txt
python run.py
```

CLI flags (full list: `python run.py -h`):

```
--joints-port      9501   client → engine: real-robot joint feedback
--twist-port       9502   client → engine: desired Cartesian motion
--velocs-host    127.0.0.1   destination host for joint-command output
--velocs-port      9503   engine → client: IK result
--gui                     enable the debug HTTP UI (off by default)
--gui-port         9504   port for the debug UI
```

## Debug UI

Add `--gui` to the command line to spin up a small HTTP server alongside
the UDP engine. Then open `http://127.0.0.1:9504` in any browser:

```
python run.py --gui
```

The page polls the engine at 20 Hz and shows:

* per-joint state (current `q` within each joint's URDF limits, with
  inversion flag) and the last-rx age
* latest Twist received (per-axis bars in [-1, 1]) and the IK mode
  flag of that packet
* latest JointCommand emitted (per-joint `q_dot` for RESOLVED_RATE or
  `q` for POSITION_IK), plus solver convergence + residual for
  POSITION_IK
* end-effector pose (FK at the current `q`) — position in metres,
  orientation as ZYX Euler in degrees

If you don't pass `--gui`, no HTTP server runs and the engine is
byte-identical to the headless baseline (one less moving part if
you're running production-style on an embedded controller).

## Wire protocol

All three sockets carry single-datagram, single-message Protobuf
payloads. The schema is `engine/messages.proto`. The bundled
`engine/proto.py` is a hand-rolled pure-Python codec (no `protoc`
needed); it's wire-compatible with code generated by any standard
Protobuf compiler — generate stubs in your language of choice from the
`.proto` file.

### Joints port (input) — `JointState`

Send the real robot's current joint positions here, as fast as you can.
The engine remembers the latest values and uses them as the starting
point for every IK solve.

```proto
message JointState {
  repeated NamedFloat joints = 1;   // entity-id keyed (see chain.json)
  uint64 t_us = 2;
}
```

`value` is in radians for revolute/continuous joints, meters for
prismatic. Joint names you don't recognize are silently ignored —
fine to send extras.

### Twist port (input) — `Twist`

Each datagram triggers exactly one IK solve and one response on the
velocs port.

```proto
enum IKMode {
  RESOLVED_RATE = 0;       // q_dot = J⁺ v  (joint velocities out)
  POSITION_IK = 1;         // integrate twist → target → DLS  (joint positions out)
}
message Twist {
  Orientation orientation = 1;   // {yaw,pitch,roll} normalized [-1, 1]
  Vector3 position = 2;          // {x,y,z} normalized [-1, 1]
  IKMode mode = 3;
  uint64 t_us = 4;
}
```

`orientation` and `position` are *normalized scalars in [-1, 1]*. The
engine scales them by `max_lin_vel` (m/s) and `max_ang_vel` (rad/s)
from `ik_profile.json` before solving. So an `(x=1, y=0, z=0)` packet
with `max_lin_vel=0.25` becomes a 0.25 m/s desired Cartesian velocity
along world +X.

### Velocs port (output) — `JointCommand`

The engine sends one of these per `Twist` it receives.

```proto
message JointCommand {
  repeated NamedFloat joints = 1;
  IKMode mode = 2;
  uint64 t_us = 3;
  bool converged = 4;            // POSITION_IK only
  float residual = 5;            // POSITION_IK only
}
```

When `mode = RESOLVED_RATE`, each `joints[i].value` is a joint
*velocity* (rad/s for revolute, m/s for prismatic).

When `mode = POSITION_IK`, each `joints[i].value` is a joint
*position* (rad, m). `converged=false` means the solver hit
`max_iter` without reaching tolerance — usually because the target
left the workspace; the residual tells you by how much.

## Tuning

`data/ik_profile.json` carries the parameters dialed in by
`Pose ▸ Train IK…` in the editor. The two velocity scaling fields
are deployment-specific (the editor doesn't know the speed envelope of
your hardware) — adjust them on the deployed engine without re-exporting:

```json
{
  "max_lin_vel": 0.25,    // m/s when |position.{x,y,z}| = 1
  "max_ang_vel": 1.00     // rad/s when |orientation.{yaw,pitch,roll}| = 1
}
```

Other knobs worth knowing:

* `damping` — Levenberg-Marquardt λ. Higher = smoother near
  singularities, lower = tighter tracking.
* `mode` — `"pose_locked"` (orientation hard-locked, default for
  spherical-wrist arms) vs `"pos_primary"` (orientation as null-space
  secondary, better for non-spherical wrists).
* `max_dq_step`, `max_total_dq_step` — caps on per-iteration and
  per-call joint motion. Lower = smoother, higher latency to converge.

The other fields (`score`, `pos_err_max_mm`, etc.) are diagnostics
written by `Train IK…` and ignored at runtime.

## Joint identity

Joint names in the wire protocol are entity IDs from the original
ForgeBOT project (e.g. `ent_joint_a3f2b1c0`) — see `chain.json` for the
authoritative list. We keep IDs (not human names) on the wire so that
renames in the editor don't silently re-map your control loop. The
human-readable name and joint type are also in `chain.json` for the
morphing layer's reference.

## Notes

* No SDP, no ICE, no protobuf compiler, no transcoding. Just UDP and
  numpy.
* The engine is stateless except for the latest `JointState` (and an
  integrated target pose for `POSITION_IK`). Restart safely at any
  time; reconnect by sending a fresh JointState.
* For >200 Hz control, prefer `RESOLVED_RATE` — it does one
  Jacobian solve per request (~0.1 ms for a 7-DOF arm).
